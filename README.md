# Прослойка к 1С:Предприятие 8.3

Программный доступ к информационной базе 1С (`<путь к базе>`, например
`C:\Bases\МояБаза`) для ИИ-агентов и внешних приложений: произвольный код 1С, запросы,
метаданные, HTTP API и MCP-сервер. Проверено на платформе 8.3.18.1208, файловая база.

**Для администратора:** порядок размещения, права и проверка —
[`docs/company/ADMIN_CHECKLIST.md`](docs/company/ADMIN_CHECKLIST.md). Ключевой принцип: доступ
ограничивается **ролью в 1С на стороне платформы**, а не обещаниями кода.

## Документация: две части в одном репозитории

Репозиторий пока смешанный, но документация уже разделена по границе будущего раскола
на два репозитория:

| Часть | Что внутри | Кому предназначена |
|---|---|---|
| `docs/core/` + код | метод работы, лимиты, инструменты, общие грабли платформы | репозиторий №1 — можно дать любому 1С-программисту |
| `docs/company/` | стенд, доступы, процессы, грабли нашей среды | репозиторий №2 — только внутрь |

Правило границы: **общая часть не ссылается на нашу, наша может ссылаться на общую.**
Поэтому в `docs/core/` нет ни адресов, ни версий, ни объёмов баз, ни процессов.

`sandbox/` — полигон для проверки моста, не продукт: см. [`sandbox/README.md`](sandbox/README.md).

В `docs/company/` не должно быть секретов: ни паролей, ни адресов и имён хостов, ни данных
людей — только описания среды и договорённостей.

Обе части лежат в этом репозитории, но живут раздельно. Когда понадобится выдать общую часть
отдельно — например, отправить одному 1С-программисту без наших внутренних заметок, — это
делается одной командой, `docs/company/` в неё не попадает:

> `git archive HEAD docs/core AGENT.md README.md bridge tools src build sandbox setup.ps1 apply_extension.ps1 -o core.zip`

## Что уже работает

| Канал | Механизм | Статус |
|-------|----------|--------|
| Произвольный код 1С | COM (V83.COMConnector) + обработка-исполнитель `build/mcpExecutor.epf` | ✅ |
| Запросы (язык запросов) | COM + `NewObject("Запрос")` | ✅ |
| Метаданные | COM + `conn.Метаданные` | ✅ |
| Управление пользователями ИБ | COM + `ПользователиИнформационнойБазы` | ✅ |
| Конфигурация: выгрузка/загрузка XML | `1cv8 DESIGNER` / `ibcmd` | ✅ |
| Сборка EPF/ERF из XML | `epf-build.ps1` (внешние навыки, см. ниже) | ✅ |
| Веб-публикация (Apache, OData, HTTP-сервисы) | `web-publish.ps1` (внешние навыки) | готово, не использовано |
| Веб-тестирование (браузер) | `web-test` (Node.js, внешние навыки) | готово, не использовано |
| MCP-сервер для LLM-агентов | `bridge/mcp_server.py` (Model Context Protocol) | ✅ |

## Быстрый старт

```powershell
# 1. Регистрация COM (делается один раз; HKCU, без админа)
powershell -NoProfile -File bridge\setup_com.ps1

# 2. Проверка моста
python -X utf8 bridge\onec.py info
python -X utf8 bridge\onec.py exec "Результат = 40 + 2;"
```

## Использование моста из Python

```python
import sys; sys.path.insert(0, "bridge")
from onec import OneC

with OneC() as c:
    print(c.info())                          # версии, конфигурация
    print(c.execute("Результат = 1 + 1;"))   # произвольный код (переменная Результат)
    print(c.query("ВЫБРАТЬ 1 КАК А"))        # запрос -> {columns, rows, ...}
    print(c.metadata("catalogs"))            # объекты метаданных
```

Ключевые правила (подробности — в `bridge/onec.py`):
- **Все COM-операции идут через один выделенный поток** — объекты 1С привязаны к апартаменту.
- Значения: примитивы как есть, даты ISO, ссылки через `XMLСтрока()` (UUID).
- Глобальные объекты внешнего соединения ограничены: `СистемнаяИнформация` и подобные
  создаются через `Новый`/`NewObject`, по имени не доступны.

## Как это было настроено (одноразовые шаги, для истории)

1. **COM**: `comcntr.dll` + typelib зарегистрированы в HKCU (см. `bridge/setup_com.ps1`),
   т.к. установка не зарегистрировала `V83.COMConnector` (нужны права админа для HKLM).
2. **Пользователь**: создан пользователь ИБ «Администратор» с ролью «ПолныеПрава»
   (роль добавлена в конфигурацию из `sandbox/src/basecfg`), пароль пустой.
3. **Защита от опасных действий**: в итоговой схеме остаётся **включённой** — снимать её
   не нужно. Исполнитель кода доставляется как объект расширения конфигурации (см. ниже),
   поэтому платформа не показывает диалог безопасности, а права ограничиваются ролью.
4. **Исполнитель кода**: `build/mcpExecutor.epf` собран из `src/executor` внешним скриптом
   `epf-build.ps1` (формат 2.11 для 8.3.18).
   Модуль: `ВыполнитьКод(Код)` через оператор `Выполнить`, результат — переменная `Результат`;
   `ВычислитьВыражение(Выражение)` через `Вычислить`.

## Внешние навыки (cc-1c-skills)

Скрипты сборки/выгрузки взяты из публичного репозитория навыков
[`Nikolay-Shirokov/cc-1c-skills`](https://github.com/Nikolay-Shirokov/cc-1c-skills)
(в этот репозиторий не входит — клонируется отдельно). Вызов напрямую из PowerShell:

```powershell
# Собрать обработку из XML-исходников
powershell -NoProfile -File <cc-1c-skills>\.claude\skills\epf-build\scripts\epf-build.ps1 `
  -InfoBasePath <путь к базе> -UserName Администратор `
  -SourceFile src\executor\mcpExecutor.xml -OutputFile build\mcpExecutor.epf

# Выгрузить конфигурацию в XML
1cv8 DESIGNER /F <путь к базе> /DumpConfigToFiles sandbox/src/cfg /Out dump.log /DisableStartupDialogs
```

База зарегистрирована в `.v8-project.json` (id: `dev`) — скилы, читающие этот файл,
автоматически используют платформу 8.3.18 и пользователя Администратор.

## Проверочный стенд (sandbox/)

Чтобы проверить мост, не трогая рабочую базу, в репозитории есть маленькая учебная
конфигурация — `sandbox/`. Это полигон: в нём разрешено то, что запрещено на рабочем
стенде (запись, проведение, движение регистров, свободный `exec`, применение расширений).

Зачем он нужен: правки `bridge/`, обработки-исполнителя и C#-моста проверяются здесь,
а не на базе заказчика; и любой, кто клонировал репозиторий, может убедиться, что мост
работает end-to-end, не имея своей базы 1С.

Чем он **не** является: ни демонстрацией, ни образцом, ни приближением к реальной
конфигурации. Он не показывает ни объёмов данных, ни легаси, ни поведения на больших
таблицах — настоящая проверка делается на тестовой базе у заказчика. Данные и порядок
воссоздания — в [`sandbox/README.md`](sandbox/README.md).

Быстрая проверка моста:

```powershell
$env:ONEC_CONNECTION_STRING = 'File="<путь к полигону>";Usr="Администратор";Pwd=""'
python -X utf8 bridge\onec.py check          # исполнитель и запросы
python -X utf8 tools\mcp_test.py             # MCP-инструменты (нужен venv проекта)
```

## Расширение «ИИМост» — работа при включённой защите

Обработка-исполнитель добавлена в базу как объект **расширения конфигурации**
(`src/cfe/ИИМост`, объект `ИИМост_ИсполнительКода`). Это штатный способ доставки кода
в базу, который снимает проблему боевых баз:

- **внешний EPF** блокируется «Защитой от опасных действий» (если она включена);
- **объект расширения** доступен во внешнем соединении при **включённой** защите —
  снимать галочку администратору НЕ нужно, достаточно один раз применить расширение;
- какие операции при этом доступны, определяет роль пользователя ИБ, а не расширение.

Мост `bridge/onec.py` автоматически использует расширение, а EPF — как fallback.
Проверено: пользователь «СЗащитой» (защита ВКЛ по умолчанию) исполняет код через расширение,
а загрузка внешнего EPF у него блокируется.

Применение расширения к базе (8.3.18, параметр слитно — см. `docs/core/PITFALLS.md` #26):
```powershell
1cv8 DESIGNER /F "<путь к базе>" /N"Администратор" /P"" /LoadConfigFromFiles "src\cfe\ИИМост" -Extension"ИИМост" /Out l.log /DisableStartupDialogs
1cv8 DESIGNER /F "<путь к базе>" /N"Администратор" /P"" /UpdateDBCfg -Extension"ИИМост" /Out l.log /DisableStartupDialogs
```

## Мост без Python и PowerShell (C#)

Если на рабочей машине нет Python, а запуск скриптов PowerShell ограничен политикой,
используется `bridge\bin_fd\onec.exe`. Исходники — `src/onec-cs`, сборка одной командой:

```powershell
dotnet publish src/onec-cs -c Release -o bridge/bin_fd
```

Самодостаточный вариант (на машине не нужен .NET; ~70 МБ, в репозиторий не входит):

```powershell
dotnet publish src/onec-cs -c Release -r win-x64 -p:SelfContained=true -p:PublishSingleFile=true -o bridge/bin
```

Использование (результат — в stdout, ход работы — в stderr):

```powershell
$env:ONEC_CONNECTION_STRING = 'File="C:\Bases\МояБаза";Usr="Имя";Pwd=""'
bridge\bin_fd\onec.exe check
bridge\bin_fd\onec.exe info
bridge\bin_fd\onec.exe query "ВЫБРАТЬ 1 КАК А"
bridge\bin_fd\onec.exe exec "Результат = 6 * 7;"
bridge\bin_fd\onec.exe meta catalogs
```

Строка соединения берётся из аргумента `-cs '...'` либо из `ONEC_CONNECTION_STRING`.

## MCP-сервер — 1С как инструмент для LLM-агентов

`bridge/mcp_server.py` оборачивает мост в стандартный MCP (Model Context Protocol).
Любой MCP-клиент (Claude Code, Cursor, DSH и др.) получает четыре инструмента:

| Инструмент | Что делает |
|-----------|------------|
| `info` | версии платформы, конфигурация, строка соединения |
| `query` | язык запросов 1С → {columns, rows} |
| `execute` | произвольный код 1С (переменная `Результат`) |
| `metadata` | объекты метаданных конфигурации |

Прикладных (бизнес-) инструментов в сервере нет: состав операций под конкретную задачу
определяется отдельно, а узкие операции с ограничениями описаны в
[`docs/core/TOOLS.md`](docs/core/TOOLS.md).

Запуск (venv обязателен — системный pip не может ставить exe в `C:\Python311\Scripts`):
```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install "mcp<2" pywin32
.\.venv\Scripts\python bridge\mcp_server.py
```
Подключение (Claude Code `.mcp.json`):
```json
{ "mcpServers": { "1c-mcp": {
    "command": "C:\\<путь к репозиторию>\\.venv\\Scripts\\python.exe",
    "args": ["C:\\<путь к репозиторию>\\bridge\\mcp_server.py"],
    "env": { "ONEC_CONNECTION_STRING": "File=\"C:\\Bases\\МояБаза\";Usr=\"Имя\";Pwd=\"\"" } } } }
```

**Важно:** клиенты MCP (SDK `mcp`) по умолчанию **не пробрасывают** переменные окружения
процесса в запускаемый сервер — строку соединения нужно указать в `env` (как выше)
либо зашить в конфиг. Иначе сервер поднимется, но подключение к базе не пройдёт.
Конфигурация через env: `ONEC_CONNECTION_STRING`, `ONEC_FILE`/`ONEC_USR`/`ONEC_PWD`, `ONEC_EXECUTOR_EXT`.

## Безопасность

Гарантия ограничения — **на стороне платформы**, в роли 1С, назначенной отдельному
пользователю ИБ. Мост не имеет собственных «обещаний безопасности»: сколько прав
в роли, столько и доступно, остальное отклоняет платформа.

- отдельный пользователь ИБ для агента, роль с правом **«Внешнее соединение»**
  и правами **только на чтение** (без прав администрирования, без записи и проведения);
- роль `ПолныеПрава` для агента **не выдаётся**;
- доступ к кластеру 1С, СУБД и хранилищу конфигурации **не требуется и не запрашивается**;
- все обращения агента видны в **журнале регистрации** 1С и в сессиях под отдельным
  пользователем — по ним видно, что именно выполнялось;
- расширение конфигурации применяется один раз штатной операцией и не ослабляет
  «Защиту от опасных действий».

Проверка для администратора: под пользователем агента чтение работает, а попытка записи
отклоняется платформой. Подробнее — [`docs/company/ADMIN_CHECKLIST.md`](docs/company/ADMIN_CHECKLIST.md).

## Структура

```
setup.ps1            # диагностика окружения и первичная настройка
apply_extension.ps1  # применение расширения к базе (один раз)
bridge/              # продукт: мост к 1С
  onec.py            # ядро: подключение, execute/query/metadata/info
  onec.ps1           # то же на PowerShell 5.1 (без Python)
  bin_fd/onec.exe    # C#-мост (не требует Python и PowerShell); bin/ — самодостаточная сборка
  mcp_server.py      # MCP-сервер (info, execute, query, metadata)
  remote.ps1         # работа с удалённой машиной по SSH
  setup_com.ps1      # регистрация COM в HKCU
  cluster.py         # администрирование своего тестового кластера (опционально, у заказчика не нужно)
src/                 # продукт: исходники
  onec-cs/           # исходники C#-моста (Program.cs, onec-cs.csproj)
  executor/          # XML-исходники обработки-исполнителя (EPF, fallback)
  cfe/ИИМост/        # расширение: обработка-исполнитель (защита остаётся включённой)
build/
  mcpExecutor.epf    # собранная обработка-исполнитель
tools/               # проверки продукта (mcp_test.py, check_ps_bom.ps1, ssh_exec.py)
sandbox/             # полигон: учебная конфигурация для проверки моста (см. sandbox/README.md)
map/                 # карта разведки: что уже исследовано (см. docs/core/PLAYBOOK.md)
docs/
  core/              # → будущий репозиторий №1 (можно дать любому 1С-программисту)
    DAY_ONE.md       # первый день на новом стенде: проверки, каналы, стоп-условия
    PLAYBOOK.md      # метод: инкремент, гейт по задаче, карта, спеки
    LIMITS.md        # лимиты, запреты, что делать при отказе
    TOOLS.md         # поверхность инструментов и их гарантии
    PITFALLS.md      # общие грабли платформы, COM, PowerShell, запросов
  company/           # → будущий репозиторий №2 (внутренний, компании)
    ENVIRONMENT.md   # стенд заказчика: конфигурация, объём, архитектура
    ACCESS.md        # что разрешено агенту и как нас останавливают
    PROCESSES.md     # процессы, согласования, эскалация
    STAND_NOTES.md   # грабли среды заказчика
    WORKSTATION.md   # наши машины, полигон, эксперименты
    ADMIN_CHECKLIST.md  # памятка для администратора (права, размещение, проверка)
AGENT.md             # правила работы агента (входная точка для него)
cc-1c-skills/        # клон внешнего репозитория навыков (в git не входит)
```

## Что можно добавить дальше

- **Веб-публикация** (`web-publish`): веб-клиент, OData (`/odata/standard.odata`),
  HTTP-сервисы (`/hs/...`) — тогда доступ станет доступен по HTTP.
- **Серверный режим** (ragent/rphost + 1cv8s): если понадобится кластер/многопользовательский
  доступ по сети; файловая база для этого не требует сервера.
