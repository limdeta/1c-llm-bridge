# SPEC: снимок кода конфигурации (code snapshot)

Статус: **черновик, до получения VM**. Написан по `PLAYBOOK.md` §6. Пока VM нет, часть чисел
здесь — оценки, помеченные `(оценка)`; после первого прогона на реальном `.cf` они заменяются
фактами.

## Цель

Дать агенту возможность читать исходный код конфигурации (модули объектов, менеджеров, форм,
общие модули) **без Конфигуратора, без монопольного режима и без полной выгрузки в дерево
файлов**, и при этом понимать, когда снимок устарел.

## Входит

- Получение контейнера `.cf` из базы (`DESIGNER /DumpCfg` или `ibcmd config export` — что есть в
  версии платформы).
- Разбор контейнера готовым ядром `v8unpack` (MIT, Python) — **свой парсер не пишем**.
- Стадии конвейера: `acquire → unpack → inventory → search → read → diff → cleanup`.
- Детектор изменений по слоям 0–4 из `MODES.md`; приоритет — номер версии хранилища.
- Инвентарь объектов (типы, имена, реквизиты) как артефакт в репозитории (`map/`).
- Чтение одного модуля по запросу, с лимитом объёма.

## НЕ входит

- **Любая запись в базу** и применение изменений конфигурации.
- **Установка расширения-исполнителя.** Это отдельный запрос (`ADMIN_CHECKLIST.md`), и он даёт
  `exec`, а не чтение кода: снимок работает и **без** расширения — см. `MODES.md`.
- **Захват объектов в хранилище** (`/ConfigurationRepositoryLock` и цикл «захват → правка →
  коммит»). Отдельная тема, сильно позже, отдельное согласование: в batch-режиме захват со
  списком берёт всё дерево (грабля №41) и останавливает работу программистов.
- **Декомпиляция защищённых модулей вендора** — не нужна.
- Автоматизация чтения **данных** — для этого есть живой режим (`MODES.md`), снимок тут не
  участвует.
- Веб-публикация, OData, доступ к СУБД — вне области.

## Вопросы, на которые отвечает спека

1. Как получить исходник конкретного модуля, не выгружая конфигурацию в дерево?
2. Как понять, что снимок устарел, не читая его целиком?
3. Что именно попадает в репозиторий, а что остаётся на VM?
4. Сколько это стоит по времени, диску и контексту агента?

## Критерии приёмки

Проверяемые человеком, а не «стало понятнее»:

1. На VM по имени объекта и имени модуля команда возвращает **исходный код этого модуля** и
   ничего больше.
2. Код совпадает с независимым источником: на `.epf`/`.cfe` из репозитория проверено
   байт-в-байт (см. `1c-unpack-poc.md`); на `.cf` сверить один модуль с Конфигуратором руками.
3. Детектор изменений на неизменённой конфигурации даёт «изменений нет» **без распаковки**.
4. После правки конфигурации человеком детектор указывает **изменённые объекты по именам**.
5. В репозитории после прогона нет ни одного файла с исходным кодом конфигурации.
6. Агент получает в контекст не более одного модуля за шаг.

## Бюджет

| Ресурс | Ограничение |
|---|---|
| Вызовов на разведочную задачу | ~40 (`LIMITS.md`), как и раньше |
| Модулей за шаг | 1, до 8000 символов на процедуру (`LIMITS.md`) |
| Время `unpack` реального `.cf` | `(оценка)` минуты; замер на VM |
| Диск на VM | 2 поколения контейнеров + временная распаковка одного; замер на VM |
| Трафик до харнеса | только запрошенный модуль, ничего больше |

## Самый тяжёлый запрос и чем останавливаем

Тяжелее всего — **полная распаковка контейнера** (точечной распаковки не существует, см.
`PITFALLS.md`). Она идёт на VM, в отдельный временный каталог, не в репозиторий и не в контекст.
Останавливаем так:

- распаковка запускается только когда детектор изменений сказал «есть изменения» либо когда
  нужен модуль, которого нет в текущем снимке;
- каталог распаковки удаляется по завершении задачи;
- при выгрузке с реальной базы — окно времени по согласованию (`LIMITS.md`), как для любой
  «шумной» операции.

## Риски и откат

| Риск | Что делаем |
|---|---|
| Снимок устарел, агент читает не тот код | детектор изменений + обязательная отметка «снимок от <дата>, версия хранилища N» в каждом факте карты |
| Выгрузка задела работающих людей | выгрузка не изменяет конфигурацию и не требует монопольного режима; выполняется в согласованное окно; захват объектов не используется вовсе |
| Формат `.cf` не разбирается текущим ядром (8.3.24+) | перейти на форк с патчем `detect_format`; в крайнем случае — выгрузка в дерево файлов как аварийный путь (решение человека) |
| Утечка кода конфигурации наружу | разбор только на VM; в репозиторий — инвентарь и сводки, никогда код; защищённые модули не читаем |
| Конвейер «поехал» и съел ресурсы VM | стадии раздельные и запускаются по одной; лимиты в конфиге |

**Откат:** удалить временный каталог распаковки и снимок на VM. Конфигурацию и базу наш конвейер
не изменяет, поэтому откатывать в базе нечего.

## Архитектура: стадии

Каждая стадия — отдельная заменяемая функция; ядро спрятано за интерфейсом (смейнить
`v8unpack` на форк — правка одной функции).

| Стадия | Вход | Выход | Где |
|---|---|---|---|
| `acquire` | параметры базы | `.cf` | VM |
| `unpack` | `.cf` | дерево `Тип/Имя/{*.json,*.obj.bsl,*.mgr.bsl}` | VM, temp |
| `inventory` | дерево | JSON: объекты, типы, реквизиты | VM → репозиторий |
| `search` | шаблон | адреса совпадений (файл + строка), **не тексты** | VM |
| `read` | объект + модуль | исходник одного модуля | VM → агент |
| `diff` | два дерева или два `configinfo` | список изменённых объектов | VM |
| `cleanup` | — | удаление temp | VM |

Пример конфига (черновой, до прогона на VM):

```yaml
core: v8unpack                  # заменяемое ядро
containers_dir: C:\1c-work\cf   # два поколения контейнеров (.cf)
work_dir: C:\1c-work\temp       # временная распаковка, удаляется по завершении
state_dir: C:\1c-work\state     # инвентарь, хэши, сводки diff
keep_generations: 2             # текущее + предыдущее, чтобы diff всегда был возможен
limits:
  module_bytes: 8000            # как в LIMITS.md
  search_hits: 200              # адреса совпадений, не тексты
  processes: 2                  # параллелизм распаковки; тюнинг по CPU на VM
```

## Открытые вопросы к администратору

1. Как именно получать `.cf` на нашей VM: `DESIGNER /DumpCfg` или `ibcmd config export` (зависит
   от версии платформы).
2. Связана ли наша копия базы с хранилищем конфигурации, и нужны ли выгрузке репозиторные
   параметры (грабля №40).
3. Окно времени для выгрузки и её допустимая длительность (`ENVIRONMENT.md`, п. 6).
4. Версия платформы: от неё зависит выбор ядра разбора (штатный релиз или форк с `detect_format`).
5. **Диск на VM.** Нужно место под два поколения `.cf` и под временную распаковку одного из них.
   Для крупной конфигурации распакованное дерево в разы больше самого контейнера — конкретный
   объём измерить на первом же прогоне и сообщить администратору.
6. Есть ли на VM Python и разрешено ли доустановить пакеты (`pip`), или конвейер должен обойтись
   тем, что есть.
